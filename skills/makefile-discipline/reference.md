# Makefile Discipline — reference

> Companion to `SKILL.md`. Patterns and conventions for Make-driven Symfony projects, distilled from the agency/Smile boilerplate family.

## 1. Anatomy of a boilerplate split

```
repo/
├── Makefile               ← framework (regenerated by the boilerplate bump)
├── Makefile-solution      ← project — edit here
├── docker/
│   ├── php/Makefile       ← per-service (rarely edited)
│   ├── postgres/Makefile
│   └── redis/Makefile
└── conf/
    ├── .env.global        ← NAME=foo, SERVICES=postgres redis php, BOILERPLATE_VERSION=...
    ├── .env.php
    └── .env.<service>
```

`Makefile` typically:
- Loads env via `wildcard $(ENV_DIR).env*`.
- Computes `COMPOSE_PROJECT_NAME` (worktree-aware).
- `include Makefile-solution`.
- Loops `$(SERVICES)` to `-include $(DOCKER_DIR)/$(1)/Makefile` and to append each service's `docker-compose.yml` to `COMPOSE_FILE`.
- Provides the generic Docker targets: `up`, `down`, `build`, `ps`, `logs`, `go`, `config`, `ips`, `clean`, `uninstall`, `reinstall`.
- Provides the help target (the awk script — see §3).

`Makefile-solution` typically:
- `console`, `migrations`, `migrations-diff`, `fixtures-load`.
- `quality`, `tests`, `tests-full`, `coverage`, `ci`, `ci-full`.
- `assets-dev`, `assets-prod`.
- Anything project-specific (e.g. `make worktree-add`, `make self-validation-reset`).

`docker/<service>/Makefile` typically:
- The `$(php)` / `$(composer)` variables used by `Makefile-solution`.
- A `clean::` double-colon target that wipes the service's data.

## 2. `$(MAKEFILE_LIST)` and `make help`

The help target is usually defined in `Makefile`:

```makefile
.DEFAULT_GOAL := help

help:
	@awk 'BEGIN {FS = ":.*##"; printf "Usage: make \033[36m<target>\033[0m\n"} \
	  /^[a-zA-Z_-]+:.*?##/ { \
	    split($$2, a, "##"); \
	    match(a[1], /\[.*\]/); if (RLENGTH) {sub(/\[.*\]/, "\033[33m&\033[0m", a[1])}; \
	    match(a[2], /\[.*\]/); if (RLENGTH) {sub(/\[.*\]/, "\033[33m&\033[0m", a[2])}; \
	    printf "\033[36m%-25s\033[0m %s\n", $$1, a[1]" "a[2] \
	  } \
	  /^##@/ { printf "\n\033[1;4m%s\033[0m\n", substr($$0, 5) }' $(MAKEFILE_LIST)
```

Key insight: `$(MAKEFILE_LIST)` expands to **all** files Make has loaded — the primary `Makefile`, every `include` directive, plus auto-loaded files. So `make help` aggregates targets from:
- `Makefile`
- `Makefile-solution`
- `docker/postgres/Makefile`
- `docker/maildev/Makefile`
- `docker/redis/Makefile`
- `docker/php/Makefile`

…and any other included file. Adding a target with the `##` helptext convention anywhere in this set makes it appear in `make help` automatically.

## 3. Target naming convention

```makefile
##@ Group Name                          # section header (shown bold underlined in help)

target:        ## [arg] [arg2]          [tag] free-form helptext
target:
	command...

migrations: ##                          Execute Doctrine migrations
	@$(call run_in_php_project,php bin/console doctrine:migrations:migrate --no-interaction)
```

- `##@` defines a group (visually separates sections in `make help`).
- `##` after the target name defines helptext (parsed by the awk script).
- `[bracketed]` words inside the helptext get highlighted in yellow (a visual hint about positional args).
- Empty `##` (no helptext) still shows the target — useful for double-colon targets that extend a base.

Common groups: `Docker`, `Production`, `Symfony`, `Worktrees`, `CLI Builder`, `Self-validation`, `Assets`.

## 4. Passing extra args — the `MAKECMDGOALS` trick

`make console cache:clear --env=prod` is **two** Make goals: `console` and `cache:clear --env=prod`. Without help, Make would try to build a target named `cache:clear`. The idiom is:

```makefile
console:
	$(php) ${SERVICES_PHP_PROJECT_DIR}/bin/console $(wordlist 2,$(words $(MAKECMDGOALS)),$(MAKECMDGOALS))
	@:

# Catch-all for the extra "goals" so Make doesn't complain
%:
	@:
```

- `$(wordlist 2,$(words X),X)` returns everything from word 2 onward — the args passed after the main target.
- `%: @:` is a wildcard rule that turns the extra args into no-op targets so `make` doesn't fail with "no rule to make target".

For multi-word args with spaces, special chars, or shell-significant tokens, this can break. Document a direct `docker compose exec` fallback in the project's CLAUDE.md (samurai does this).

## 5. The `$(call run_in_php_project, ...)` idiom

When the Symfony app lives in a sub-dir (`symfony/`, `app/`, `backend/`) but Docker mounts the project root, you need to `cd` inside the container before running the command. The boilerplate exposes a `call` function:

```makefile
# Defined in Makefile-solution (or a per-service Makefile)
define run_in_php_project
docker compose run --rm php sh -lc "cd ${SERVICES_PHP_PROJECT_DIR} && $(1)"
endef

# Used by every Symfony-side target
migrations: ##                          Execute Doctrine migrations
	@$(call run_in_php_project,php bin/console doctrine:migrations:migrate --no-interaction)
```

Why a function and not a static prefix:
- `$(call ...)` lets you pass a multi-token command without quoting hell.
- Switching between `docker compose run --rm` and `docker compose exec` (or to Kubernetes) is one edit.
- Per-env overrides become trivial.

Note: commas inside the call argument must be escaped — define `comma := ,` and use `$(comma)` because Make splits `$(call X,Y)` raw arguments on commas.

```makefile
comma := ,

tests: ##                               PHPUnit Unit + Functional + Api
	@$(call run_in_php_project,XDEBUG_MODE=off php vendor/bin/phpunit --testsuite=Functional$(comma)Api)
```

## 6. `COMPOSE_FILE` aggregation

Multi-service Compose setups use **one base file per service**, aggregated via `COMPOSE_FILE`:

```makefile
TMP_COMPOSE_FILE=docker-compose.yml
$(foreach service,$(SERVICES),$(eval TMP_COMPOSE_FILE := $$(TMP_COMPOSE_FILE):$(DOCKER_DIR)/$(service)/docker-compose.yml))
export COMPOSE_FILE=${TMP_COMPOSE_FILE}:docker-compose.yml
```

Effect: `docker compose` reads `docker-compose.yml`, then each `docker/<service>/docker-compose.yml`, then `docker-compose.yml` again. The trailing root file lets the project override service settings (volumes, labels) without touching the per-service files.

This is why **calling `docker compose ps` directly from outside Make returns nothing meaningful** — the `COMPOSE_FILE` env var isn't set. Always go through `make` (or replicate the env vars in your invocation).

## 7. Worktree-aware `COMPOSE_PROJECT_NAME`

To run multiple worktrees in parallel without container/volume collisions:

```makefile
export COMPOSE_PROJECT_NAME := $(if $(filter $(NAME),$(notdir $(CURDIR))),$(NAME),$(NAME)-$(notdir $(CURDIR)))
```

- On the main checkout (e.g. `samurai/`), `notdir $(CURDIR)` is `samurai` → matches `$(NAME)` → project name is just `$(NAME)`.
- On a worktree (e.g. `samurai/.claude/worktrees/feat-x/`), `notdir $(CURDIR)` is `feat-x` → doesn't match → project name is `samurai-feat-x`.

This is invisible to most Make targets but **critical** for any custom target that touches Docker resources by name (volumes, networks, Traefik routers).

## 8. Double-colon targets for hooks

`clean::` (double colon) allows multiple Makefiles to **append** to the same target without overriding each other:

```makefile
# In Makefile
clean::    ##                      Remove project dependencies
clean::

# In Makefile-solution
clean::
	chmod u+w some/path

# In docker/php/Makefile
clean::
	rm -rf vendor
```

`make clean` runs **all three** bodies in order. Use this for any composite teardown target.

## 9. Production vs dev compose

Common convention: `docker-compose.prod.yml` + `.env.prod`. Prod targets pin the project name explicitly so volumes stay stable:

```makefile
prod_compose = docker compose -p $(NAME) -f docker-compose.prod.yml --env-file .env.prod

prod-up:
	$(prod_compose) up -d --wait
```

Prod targets must **not** rely on `COMPOSE_PROJECT_NAME` (which is worktree-aware and would diverge per checkout).

## 10. Patterns to add new targets safely

### Adding a new Symfony command shortcut

```makefile
# In Makefile-solution, under ##@ Symfony
cache-clear: ##                         Clear Symfony cache
	@$(call run_in_php_project,php bin/console cache:clear)
```

Pass `--env=prod` if needed via the `MAKECMDGOALS` idiom.

### Adding a quality gate

```makefile
# In Makefile-solution, under ##@ Quality (create the group if missing)
##@ Quality

deptrac: ##                             Run Deptrac architecture check
	@$(call run_in_php_project,php vendor/bin/deptrac analyse --no-progress)
```

`make help` will pick it up automatically.

### Adding a worktree helper

```makefile
# In Makefile (worktree section is framework-level on most boilerplates,
# so check if the project already has one before adding here vs in solution)
worktree-list: ##                       List active worktrees
	@git worktree list
```

If the framework `Makefile` already defines `worktree-add` / `worktree-remove`, add `worktree-list` to **`Makefile-solution`** (not the framework) — to survive a boilerplate bump.

## 11. Anti-patterns

- ❌ **Editing the framework `Makefile`** when `Makefile-solution` exists — wiped at next boilerplate bump.
- ❌ **`cd path/ && cmd` in a target body** — breaks parallel runs (Make is parallel-safe at target level, not at recipe-line level). Use `$(call run_in_php_project,...)` or `(cd path && cmd)` in a sub-shell.
- ❌ **Hardcoding `docker compose exec <service>`** — kills the `$(call run_in_php_project,...)` abstraction and locks the target to a specific Docker layout.
- ❌ **`##` helptext on `.PHONY` declarations** — the awk script doesn't parse them; only the recipe line gets it.
- ❌ **Targets without `##` helptext** — invisible in `make help`, so other devs (and Claude) won't discover them.
- ❌ **Using single-colon `:` when extending a base target** from another file — overrides instead of appending. Use `::` for hook-style composition.
- ❌ **Forgetting the `comma := ,` trick** — `$(call X,a,b)` splits on raw commas; escape with `$(comma)` when the argument itself contains a comma.
- ❌ **Using `$(MAKEFILE_LIST)` after a recursive `$(MAKE)`** — the variable resets in the sub-make. Read it eagerly at the top.

## 12. Validation commands

```bash
make help                       # Should show all targets grouped + with helptext
make -n <target>                # Dry-run a target without executing
make -pRrq 2>/dev/null | less   # Dump Make's internal database (targets, vars, rules)
make config                     # Most boilerplates: dump merged Compose config
make ps                         # Show container status (Make sets COMPOSE_FILE correctly)
```
